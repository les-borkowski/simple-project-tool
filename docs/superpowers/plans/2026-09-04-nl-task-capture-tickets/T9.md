# T9 — Docs: eval results, env vars, feature docs

[← index](README.md) · source: [full plan](../2026-09-04-nl-task-capture-and-eval-harness.md)

---

**Type:** docs
**Goal:** a reader arriving at the README understands what was measured, how, and where it is weak —
without running anything.
**Difficulty:** easy
**Depends on:** T3, T5
**Acceptance criteria:**
- [ ] README gains a capture section: what it does, the preview→confirm guarantee, and the exact
      commands to run the evals
- [ ] The per-field and per-tag tables from `backend/evals/results/latest.md` are pasted in, with the
      model id, prompt version and run date stated
- [ ] **Weak fields are named in prose**, not just left in a table — including whatever Polish
      relative-date scoring actually came out at
- [ ] The method is explained in a short paragraph: alignment then per-field scoring, why not exact
      match, and why no LLM judge (D10)
- [ ] All five env vars are documented with the note that an empty `GOOGLE_API_KEY` disables the
      feature; no key value appears anywhere
- [ ] The privacy position is stated: capture text plus member display names and story names go to
      the provider, and free-tier terms may allow their use for product improvement (§2.7, §2.8)
- [ ] `docs/architecture.md` gains the capture flow and the `app/core/llm/` layer
**Files in scope:** `README.md`, `docs/architecture.md`, `docs/changelog.md`.
**Constraints:** every number in the README comes from a committed `latest.md` — no numbers typed
from memory, no rounding up. Failing cases stay published.
**Verification:** the pasted tables match `backend/evals/results/latest.md` exactly; a fresh reader
can go from README to a passing `uv run python -m app.evals.run` with no other instructions.
**Out of scope:** blog-style writeup; screenshots (nice-to-have, add later if T8 landed).
