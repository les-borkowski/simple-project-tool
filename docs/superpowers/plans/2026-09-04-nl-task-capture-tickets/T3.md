# T3 — Eval harness: cases, scorer, runner, CI gate

[← index](README.md) · source: [full plan](../2026-09-04-nl-task-capture-and-eval-harness.md)

---

**Type:** backend
**Goal:** one command scores the extractor field by field against a versioned case file and prints a
table — including its failures — and CI enforces the numbers for free.
**Difficulty:** hard — the aligner and the null-handling are subtle, and a scorer that is quietly
wrong is worse than no scorer at all.
**Depends on:** T2
**Acceptance criteria:**
- [ ] `backend/evals/cases/capture.jsonl` holds ~35 cases with a `_meta` header line, distributed:
      6 relative-date · 5 missing/ambiguous assignee · 5 multi-task · 4 not-a-task · 6 Polish ·
      3 story-association · 2 injection-shaped · 4 long/messy. Every case carries its own
      `reference_date`, `fixture`, and `tags`.
- [ ] Alignment: predicted tasks are matched to expected greedily by title token-set F1 (highest
      first); unmatched expected count as misses, unmatched predicted as spurious
- [ ] Per-field scores over aligned pairs — `count` (binary), `title` (F1 ≥ 0.6 = hit, mean F1 also
      reported), `due_date`, `assignee`, `story`, `priority` (exact, **null-aware: `null == null` is
      a hit**), `not_a_task` (negative cases only) — aggregated micro **and per tag**
- [ ] `uv run python -m app.evals.run` works offline against recorded fixtures; `--live`, `--record`,
      `--filter <tag>`, `--format md|json` and `--delay` all behave as named; `--record` runs
      **sequentially** with 429 backoff and leaves no half-written fixture set on failure
- [ ] `backend/evals/results/latest.md` contains a run header (model, prompt version, mode, date,
      case count, tokens), the per-field table, the per-tag table, and then **every failing case in
      full** — input, expected, actual, which fields missed. There is no flag that hides failures.
- [ ] `tests/test_evals.py` runs the harness in replay mode, asserts the floors in
      `backend/evals/thresholds.json`, and separately asserts that replay mode cannot construct a
      real HTTP client
**Files in scope:**
`app/evals/__init__.py`, `run.py` (argparse CLI), `score.py` (aligner + field metrics), `report.py`
(markdown/JSON rendering); `backend/evals/cases/capture.jsonl`;
`backend/evals/fixtures/projects.json`; `backend/evals/fixtures/responses/*.json`;
`backend/evals/thresholds.json`; `backend/evals/results/latest.{md,json}`;
`tests/test_evals.py`; `.github/workflows/evals.yml`.
**Constraints:**
- **JSONL, not YAML** — `pyyaml` is not a dependency and must not become one. `argparse`, not a new
  CLI framework; `pytest`, not a new runner.
- Fixture cache key is `sha256(provider|model|prompt_version|rendered system|rendered user)`, so a
  prompt edit *must* invalidate recordings and fail the replay run loudly.
- Fixture projects are fictional — no real project or member data leaves the machine (§2.8).
- `evals.yml` is `workflow_dispatch:` only, reads `GOOGLE_API_KEY` from repo secrets, uploads
  `latest.md` as an artifact, and is `continue-on-error: true`. **No `schedule:` trigger.**
- The scorer imports nothing from `app.api.routes` or `app.db`, and the eval run touches no database.
**Verification:**
- `uv run python -m app.evals.run` → table printed, exit 0, no network (verifiable by running with
  networking off)
- `uv run pytest tests/test_evals.py` passes; deliberately lowering a threshold's actual score makes
  it fail
- one `--record` run against the live API, then a replay run reproducing identical numbers
**Out of scope:** LLM-as-judge scoring; `n>1` sampling; any endpoint.
