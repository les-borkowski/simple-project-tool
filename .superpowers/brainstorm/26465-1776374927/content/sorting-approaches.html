A

Client-side sort (recommended)

Sort the items already loaded in the browser. No backend changes needed. Works instantly — just re-orders the state array when the user picks a field.

Pros

  • Zero backend changes
  • Instant — no network round-trip
  • Fully reversible / no state to persist

Cons

  • Only sorts items already loaded (not cross-page)
  • Default load order is always created_at DESC
B

Server-side sort

Add order_by and order_dir query params to stories and tasks list endpoints. Correct sorting across all pages, regardless of pagination.

Pros

  • Works correctly with pagination
  • Consistent results for large datasets

Cons

  • Requires backend API + DB query changes
  • Cursor-based pagination breaks with non-date sort fields (needs redesign)
  • More moving parts
C

Client-side + load all

When user picks a sort field, fetch all items at once (remove pagination). Sort in the browser. Re-enable pagination only when sort is cleared.

Pros

  • Correct sort across all items
  • Minimal backend changes (just add a high limit)

Cons

  • Could be slow for large lists
  • Complex state management (pagination ↔ no-pagination toggle)

My recommendation: Option A — lists in a project management tool rarely exceed 50–100 items per page, so client-side sort covers the practical use case cleanly. Option B adds significant complexity with marginal real-world benefit at this scale.
